## [2026-04-03] 네트워크 인터페이스 변경 후 Liveness Probe 실패

### 배경

K8s 초기 설치 시 `eth0`(외부망+클러스터망)으로 구성 → 이후 인터페이스 역할 분리

| 인터페이스 | 대역 | 역할 |
|---|---|---|
| eth0 | 10.255.254.0/24 | 외부망 (SSH, 인터넷) |
| eth1 | 192.168.0.0/24 | K8s 클러스터 내부망 |

### 문제

- kubelet이 probe 요청 시 `eth0` IP를 source로 사용
- Multus `net1`(10.255.254.x)과 노드 IP 대역이 겹쳐 비대칭 라우팅 발생
- NetworkAttachmentDefinition 템플릿에 `gateway` 설정 누락

### 원인 상세: 비대칭 라우팅

```
kubelet(10.255.254.26) → Pod eth0 도달 ✓
Pod 응답: 10.255.254.26 → net1(10.255.254.0/24) 매칭 → net1으로 잘못 나감 ✗
→ kubelet에 응답 미도달 → Probe timeout
```

### 조치

#### 1. NetworkAttachmentDefinition 템플릿 수정

```yaml
# 변경 전
"ipam": {
  "type": {{ .Values.multus.network.ipam.type | quote }}
}

# 변경 후 (gateway 필드 추가)
"ipam": {
  "type": {{ .Values.multus.network.ipam.type | quote }}
  {{- if .Values.multus.network.ipam.gateway }}
  ,
  "gateway": {{ .Values.multus.network.ipam.gateway | quote }}
  {{- end }}
  {{- if .Values.multus.network.ipam.routes }}
  ,
  "routes": {{ .Values.multus.network.ipam.routes | toJson }}
  {{- end }}
}
```

#### 2. kubelet `--node-ip` 설정 (핵심)

`/etc/sysconfig/kubelet` 각 노드별 설정:

```bash
# master (10.255.254.22)
KUBELET_EXTRA_ARGS="--node-ip=192.168.0.10"

# worker-ems01 (10.255.254.23): --node-ip=192.168.0.11
# worker-ems02 (10.255.254.24): --node-ip=192.168.0.12
# worker-app01 (10.255.254.25): --node-ip=192.168.0.13
# worker-app02 (10.255.254.26): --node-ip=192.168.0.14
# worker-app03 (10.255.254.27): --node-ip=192.168.0.15

systemctl restart kubelet
```

#### 3. Calico IP Autodetection 설정

```bash
kubectl set env daemonset/calico-node -n kube-system \
  IP_AUTODETECTION_METHOD=interface=eth1
```

적용 확인:

```bash
kubectl logs -n kube-system <calico-node-pod> | grep "autodetected IPv4"
# Using autodetected IPv4 address 192.168.0.13/24 on matching interface eth1
```

**IP_AUTODETECTION_METHOD 옵션 목록**:

```bash
interface=eth1                  # 특정 인터페이스 지정 (현재 사용)
interface=eth.*                 # 인터페이스 regex
cidr=192.168.0.0/24             # CIDR 기반
skip-interface=eth0             # 제외 방식
can-reach=192.168.0.1           # 특정 IP에 도달 가능한 인터페이스 선택
```

#### 4. Calico 변경 후 노드 재부팅 순서

Calico 설정 변경 후 모든 노드 순차 재부팅 권장:

```
worker-ems01 → worker-ems02 → worker-app01 → worker-app02 → worker-app03 → master
```

#### 4. values.yaml Multus 설정 변경

```yaml
# 변경 전
multus:
  network:
    type: "ipvlan"
    mode: "l3"

# 변경 후
multus:
  network:
    type: "macvlan"
    mode: "bridge"
    ipam:
      gateway: "10.255.254.1"
      routes:
        - dst: "192.168.15.0/24"
          gw: "10.255.254.1"
```

### 교훈

- 인터페이스 변경 시 kubelet + CNI 모두 재설정 필요
- 멀티 인터페이스 환경에서는 Calico `IP_AUTODETECTION_METHOD` 명시 필수
- `--node-ip`는 API 서버 등록용이며 실제 패킷 source IP에는 영향 없음

## [2026-04-03] Source IP 선택 문제 (미해결)

### 현황

| 항목 | 상태 |
|---|---|
| Calico eth1 사용 | ✅ 완료 |
| kubelet --node-ip 설정 | ✅ 완료 |
| Node INTERNAL-IP | ✅ 192.168.0.x |
| 실제 패킷 source IP | ❌ 여전히 eth0(10.255.254.x) |

### 원인

Linux 커널이 default route의 metric 기준으로 source IP 선택:

```
default via 10.255.254.1 dev eth0 metric 100  ← 우선순위 높음 (source IP 선택됨)
default via 192.168.0.1  dev eth1 metric 101  ← 우선순위 낮음
```

metric 값 변경 시도 시 SSH 연결 끊김(eth0가 외부 접속용) → 복구 완료

### 딜레마

- eth0 우선 → 외부 접속 가능, pod source IP 잘못됨
- eth1 우선 → pod source IP 정상, 외부 접속 불가

### 현재 판단: 현 상태로 운영

- tcp-bridge 실제 트래픽은 `net1(Multus macvlan)`으로 처리
- Pod 간 통신 정상
- Liveness probe는 허용 범위 내 (서비스 영향 없음)

### 검토 가능한 대안

1. **Policy-based Routing** - pod 대역에 대해서만 eth1 source 강제 (복잡도 높음)
2. **systemd-networkd 전환** - 더 정교한 routing 제어 가능
3. **Calico IPIP 비활성화** - direct routing 사용 (노드간 L2 연결 필요)

## [2026-04-06] worker-ems02 Multus OOM으로 Pod Sandbox 생성 실패

### 현상

`upm-ems`의 Prometheus, Alertmanager, Grafana가 `worker-ems02`에서만 기동 실패

```
FailedCreatePodSandBox
plugin type="multus-shim" failed: CmdAdd (shim): timed out waiting for the condition
failed to send CNI request: Post "http://dummy/cni": EOF
```

`worker-ems01`에서는 동일 Pod 정상 동작.

### 원인

`worker-ems02`의 `kube-multus-ds` OOMKilled:

- `limits.memory: 50Mi` → 운영 환경에서 부족
- `logLevel: "verbose"` → 메모리 사용량 증가 요인
- multus daemon 종료 → Pod sandbox 네트워크 생성 불가

### 조치

```bash
# 1. 리소스 상향
kubectl set resources -n kube-system ds/kube-multus-ds -c kube-multus \
  --limits=cpu=200m,memory=256Mi \
  --requests=cpu=100m,memory=128Mi

# 2. 로그 레벨 완화 (verbose → error)
kubectl patch configmap -n kube-system multus-daemon-config --type merge -p '{
  "data": {
    "daemon-config.json": "{\"chrootDir\":\"/hostroot\",\"cniVersion\":\"0.3.1\",\"logLevel\":\"error\",\"logToStderr\":true,\"cniConfigDir\":\"/host/etc/cni/net.d\",\"multusAutoconfigDir\":\"/host/etc/cni/net.d\",\"multusConfigFile\":\"auto\",\"socketDir\":\"/host/run/multus/\"}"
  }
}'

# 3. 재시작
kubectl rollout restart -n kube-system ds/kube-multus-ds
kubectl rollout status -n kube-system ds/kube-multus-ds --timeout=180s
```

### 결과

- `worker-ems02` multus Pod 정상 복구
- 실패했던 Alertmanager, Grafana, Prometheus 정상 기동

### 교훈

- `multus-shim` 오류가 보여도 실제 원인은 multus daemon 자체 장애일 수 있음
- 특정 노드에서만 `FailedCreatePodSandBox` 반복 시 → 노드별 CNI daemon 상태 먼저 확인
- `kube-multus-ds` memory 50Mi는 실제 운영에서 부족
- `logLevel: verbose`는 메모리 사용량 증가 요인

## [2026-04-03] tcp-bridge ipvlan L3 → L2/macvlan 전환

### 문제

```
failed to add route '{0.0.0.0 00000000} via 10.255.254.1 dev net1': network is unreachable
```

ipvlan L3 모드 + `/32` prefix → gateway가 동일 서브넷에 없어 라우트 추가 실패

### 조치

| 파일 | 변경 내용 |
|---|---|
| `values.yaml` | `mode: l3` → `mode: l2` (또는 macvlan bridge로 전환) |
| `values.yaml` | 불필요한 `10.255.254.1/32 via 0.0.0.0` 라우트 제거 |
| `deployment-0.yaml`, `deployment-1.yaml` | IP prefix `/32` → `/24` |
